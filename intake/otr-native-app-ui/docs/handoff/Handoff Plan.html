01

Where the project stands

One workflow, four canonical boards, five open explorations, nine archived ones, two PRDs, and a design system consumed as tokens plus a single component. The design work is far ahead of the delivery mechanism.

Four things are genuinely strong and should survive the move intact.

1The governance model

Workflow to workstream to board, with a closed category set of screen, component, and system. That is already a repo hierarchy.

2The decision trail

Every exploration closes in a DR, ledgers roll up, archive is append only. Most design projects never have this, and it is what makes a months long build safe.

3The DS delta discipline

The Cases manifest already names what each kit becomes in engineering terms. That document is a port map in draft.

4The design language

Status registry, signal precedence, severity hierarchy, badge form and weight. Real product logic, worked out and ratified.

02

Seven things that block a code handoff

aThere is no running app

Every artifact is a pan and zoom canvas of artboards. The README names a workflow demo as the standard and it does not exist. Nothing navigates from a feed card into that card's own detail screen. The prototype is net new assembly, not a port.

bThere is no build

Babel in the browser, IIFE modules, globals on window. Correct for boards, unusable as a deployed app: transpile on every load, no module graph, no types, nowhere to hang a test.

cThe case data is forked

CASES in cpc.jsx holds eighteen states shaped for a preview card. DETAIL in detail-kit.jsx holds a handful of landmark states shaped for a full record. They share no ids and no schema, so a card cannot open its own case.

dSnapshot duplication is heavy

design-canvas.jsx, 1,039 lines, exists in eleven places. core-kit.jsx exists in eight, in three divergent lengths. Rule 1 working as designed, and it means canon is a per file judgment call I have to make rather than something Claude Code can infer.

eProduct code and board scaffolding are tangled

DScreen, FScreen, ZLabel, explore pins, and the tweaks panel sit in the same files as the CPC, the status badge, and the action hub. The port needs them cleanly separated.

fAssets are inlined

A 71 KB base64 image inside core-kit.jsx, and 344 KB more in a text file beside it.

gThere is no review mechanism outside this tool

Pinned comments are how feedback works today. On Vercel that layer does not exist, so the CEO loop has to be designed deliberately rather than assumed.

One large piece of good news. The only thing the kits take from the design system bundle is FeatureIcon. Everything else is authored directly against token CSS variables, so the design system dependency is small and portable. That removes the usual biggest risk in a handoff like this.

03

Two trees, one repo

The repo holds two trees that must never be confused.

Sdesign/ is the studio

The board system, moved across verbatim and served as static HTML. Explorations continue exactly as they do now, unchanged.

Bapps/ and packages/ are the build

Only decided work enters here. The bridge is the decision record, as it is today. A pattern enters when a DR says adopt, and the DR records the commit and preview URL where that happened.

04

Target repo architecture

otr-native-app/
  apps/
    prototype/          Next.js App Router, TypeScript. The deployed demo.
    boards/             the design/ tree, served as static HTML on its own URL.
  packages/
    tokens/             DS token CSS, pinned and versioned, plus typed token names.
    icons/              FeatureIcon and the Streamline set, extracted from the DS bundle.
    ui/                 the OTR primitives the app actually uses.
    cases/              status registry, precedence, severity, CPC, detail zones.
    fixtures/           one typed case dataset plus named scenarios.
  design/               the board system, verbatim.
  docs/                 PRDs, decisions, ledgers, roadmap, lessons, port map.
  • Next.js App Router with TypeScript. Routing gives the demo real URLs, which is what makes a review link precise.
  • CSS Modules over the DS custom properties, no Tailwind. The design system ships tokens as CSS variables and every kit already authors against them. A utility framework would mean translating a token system that works.
  • pnpm workspaces with Turborepo. Packages keep domain logic testable on its own and stop the app from becoming the only place code can live.
  • Vitest, Playwright, GitHub Actions, Changesets. Unit tests on logic, screenshots per status, typecheck and build on every PR, a version number on every review build.

Routes: /cases the feed, /cases/[caseId] the detail screen, /cases/[caseId]/chat the privileged channel when it lands, /lab/<workstream>/<exploration> for coded explorations behind flags, and /review for the current build and what changed.

05

The demo, scoped

The thing the CEO opens on a phone.

  • Full bleed mobile web with a PWA manifest, so it installs to the home screen and runs without browser chrome. On desktop it renders inside a device frame.
  • The feed wired from the real fixture set: grouping, Active and Resolved tabs, sub chips, search, sort sheet, density.
  • Every card taps through to that case's own detail screen and back.
  • Full status coverage. All eighteen states reachable, each with its correct badge, primary action, and detail record.
  • A scenario switcher, honoring the existing rule that demo tweaks are user state cohorts and never design divergences. Personas: single incomplete case, multi case with money overdue, action needed on a legal gate, a won case, and a QA mode showing every status. Scenario travels in the URL so a review link is reproducible.
  • Session state persists locally, so unread clearing and a signed LOE survive a refresh mid review.
06

How updates, versions, explorations, and tests wire in

the part that has to hold for months
Design explorations

Continue in design/, untouched. Nothing changes about how you work today.

Coded explorations

Get a /lab route and a flag, so a divergence ships to the same preview URL without touching the canonical demo. Same BRIEF and DR discipline, same ledger.

Adoption

A pull request that moves the pattern from /lab into packages/cases, flips the DR to integrated, and deletes nothing.

Versions

Changesets and git tags. Every DR from here records the tag and preview URL it was decided on, so which version he saw is never a question.

Tests come in three tiers, in this order. Pure logic first, because it is the highest value and the easiest: badge registry completeness, primaryAction precedence, sortActions, feedGroup, urgency. Then component level per status. Then Playwright flows with a screenshot per status, which is the regression net that lets you refactor without fear.

07

The CEO review loop

  • Every pull request produces a Vercel preview URL. Nothing is reviewed on a local machine.
  • Primary path: Vercel preview comments, which pin to elements much like the comments here. Requires a seat on the Vercel team for him.
  • Fallback if he will not sign in: a small in app feedback pin that captures route, scenario, viewport, and build sha, and opens a GitHub issue through a serverless route. Two days of work, worth it only if the seat is a problem.
  • Cadence: a tagged review build with a short changelog on /review, then triage into DRs, then the roadmap. Same shape as today, on a URL instead of in a tool.

09

What I do before handoff

1Pick canon, file by file

Resolve the three divergent core-kit copies and every other duplicated kit, and record the choice in a port map. Nothing is deleted; the losing copies stay exactly where they are.

2Unify the case model

Merge CASES and DETAIL into one typed shape covering all eighteen states with the record fields the detail page needs. Ships as a spec plus a JSON fixture Claude Code imports directly.

3Extract the status registry to data

Eighteen states with badge form, weight, tone, primary action, and severity, as a JSON file rather than a component. The single highest value artifact in the handoff.

4Build Cases Demo.html

The missing workflow demo, wired from frozen kits only. Feed to detail and back, all statuses, scenario switcher. It is the reference the coded port has to match, and building it proves the unified model works before anyone writes TypeScript.

5Unpack the assets

Base64 out of source and into real image files.

6Write the handoff docs

HANDOFF, ARCHITECTURE, PORT-MAP mapping every kit to its target module, and a CLAUDE.md for the new repo carrying the rules this project runs on, including the copy standards and the never delete rule.

7Tidy the root

The orphaned record-content.jsx at the project root, plus the stray upload and screenshot folders.

11

Risks

  • The gap state badges are a known hole. Full coverage cannot be claimed until they close.
  • Merging the two fixture models will surface detail record fields never specified for the rarer statuses. Expect content decisions, not just code.
  • The design system bundle is a compiled artifact from another project. Pin a version in the repo and record it, or the port silently drifts.
  • FeatureIcon coverage and font loading need a real check on iOS Safari early, not at the end.
  • Canon selection is a design call. Claude Code must not guess it, which is why item 1 of section 9 comes first.
